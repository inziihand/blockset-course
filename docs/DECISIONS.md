# 決策紀錄與待確認項目

更新：2026-09-16。除使用者明確指定者，其餘為本次規劃採用的工程預設，可在取得新證據後調整。

## 已定方向

| 決策 | 理由／影響 |
| --- | --- |
| 首個市場為台指期，券商永豐金 Shioaji | 使用者已確認；驗收先圍繞 TAIFEX 單腿期貨 |
| 前後端同一 Monorepo | 契約、UI、Worker 可以在一次變更中審查 |
| 一個 Python 套件，API／Worker 獨立入口 | 減少初期套件發版、版本協調及跨程序狀態 |
| SDK 直接嵌入 Worker | 不額外部署 Shioaji HTTP Server；若 SDK 實測有隔離需求再評估 |
| 市場模組與券商 Adapter 分開 | TAIFEX 時段／單位是市場規則，登入／欄位／回報是券商規則 |
| 一個真實帳戶一個 Worker、最多一個主動策略 | 首版帳戶執行與風險責任清楚，台灣帳戶不假設有 subaccount |
| 本機日誌＋共享排他鎖，雲端命令與投影 | 沿用基礎設施瘦身方向，控制通道暫斷仍可維持已接受策略 |
| Firestore 作首版控制通道 | 使用既有經驗；不再並行導入 Redis、Kafka 或 Kubernetes |
| 未驗證能力不可使用 | 不把標準化介面視為所有券商都支援同樣行為 |
| 台指期單腿 MVP 先完成 | TXO、Hedged Strangle、Combo、自動換月作後續擴充 |
| API 模型產生 OpenAPI 與 TypeScript Client | 避免 Python／前端手工各自維護相同 enum |

## 尚需實測的工程事項

| 問題 | 負責階段 | 沒有答案時的做法 |
| --- | --- | --- |
| Shioaji 版本、Python／CPU／OS、Linux Docker 可行性 | P1／P2 | 不先指定正式 Worker 映像或沿用舊 VM |
| API 簽署、帳戶環境、CA、權限與模擬限制 | P2 | 只做離線測試；不請使用者把秘密貼到對話 |
| SDK callback／訂閱及查詢限額、維護時段 | P2 | 未完成實測不宣稱自動重連可用 |
| client ID、委託回查範圍、ID 跨日唯一性、Trade 重建 | P2／P3 | 未知送單保持阻塞，不憑猜測重送 |
| Cover 對超量、外部異動與反向開倉的保障 | P3 | native reduce-only 未驗證，不開放等價承諾 |
| 交易日行事曆來源更新、特殊休市資料 | P2／P6 | calendar 不完整時停止新單，顯示待更新 |
| 重連後委託／成交補查是否完整 | P3／P6 | 保存 coverage 缺口，要求對帳 |

## 後續需要產品／策略選擇的事項

- 第一個正式台指期策略的訊號、參數、執行頻率、留倉及到期處理：P7 才定稿。
- 正式風險額度、允許商品／月份、口數、損失上限：P7／P8 定稿，無預設正式送單權限。
- 部署主機、GCP project、網域及是否使用既有 Firebase 帳戶驗證：部署前確認；本次不設定舊環境為新專案預設。
- 既有手動部位接管、同帳戶多策略、其他市場優先順序：待台指期 MVP 穩定後另排。

## 明確暫緩

多主機自動接手、Active-Active、完整事件溯源平台、獨立策略微服務、插件市集、獨立 Python SDK 套件、通用回測系統、公開行情分發，以及美股／期權的實作。

目前只保留擴充需要的資料語意與介面；有第二個實際 Adapter 時再檢驗並修正抽象。
